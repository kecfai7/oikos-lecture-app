### Slide 8: The Parsing Phase: Weaving the Abstract Syntax Tree
*   **Visual Cue:** Horizontal process flow with golden chevron arrows linking String -> Parser -> AST.
*   **Slide Text:**

    *   Raw source text delivered via TCP network sockets.

*   **Professor's Script:**

V8's parser breaks down this text into lexical tokens, then builds an Abstract Syntax Tree (AST). The AST is a highly structured, hierarchical mathematical tree that represents the logical flow of the program. If the parser finds a syntax error, the execution blocks immediately."

### Slide 9: The Ignition Interpreter: Generating Bytecode
*   **Visual Cue:** A three-card layout deconstructing bytecode generation, execution speed, and profiling.
*   **Slide Text:**
    *   **AST Parsing Input**
    *   **Bytecode Emission**
    *   **Feedback Profiling**

*   **Professor's Script:**

It does not spend heavy CPU cycles optimizing; it quickly emits highly compact, memory-efficient bytecode and executes it immediately. While running, Ignition also acts as a profile monitor, keeping track of how many times a function is called and what data types are passed into it."

### Slide 10: The TurboFan JIT Compiler: Native Speed Tuning
*   **Visual Cue:** A high-contrast vertical list showcasing how TurboFan leverages feedback profiling to compile machine code.
*   **Slide Text:**
    *   **Identifying Hot Code**: Pinpointing functions called repeatedly during runtime.
    *   **Type Speculation**: Assuming variable types based on Ignition's historical profile data.
    *   **Native Machine Compilation**: Generating raw x86, ARM, or RISC-V assembly instructions.
    *   **Deoptimization Trap**: Gracefully falling back to bytecode if type speculation fails.
*   **Professor's Script:**
    "When Ignition identifies a function as 'hot'—meaning it is called repeatedly—it hands it over to TurboFan, the JIT (Just-In-Time) compiler. TurboFan uses the historical data from Ignition to make optimistic speculations about variable types. It then compiles this bytecode directly into raw machine assembly. If a speculation is violated later (e.g., passing a string instead of an integer), TurboFan executes a 'deoptimization trap,' falling back to Ignition."

### Slide 12: Memory Lifecycles: Young vs. Old Generations
*   **Visual Cue:** Two-column split cards. Left: Light cream card for Young Generation. Right: Muted navy card for Old Generation.
*   **Slide Text:**
    *   **The Young Generation Space**
    *   **The Old Generation Space**
    *   Small, highly volatile memory allocation arena.
    *   Large, persistent memory storage zone.
    *   Where newly created variables and objects are born.
    *   Where long-lived variables (e.g., app state) survive.
    *   Cleaned continuously via ultra-fast Scavenger GC.
    *   Cleaned periodically via heavy Mark-Sweep-Compact GC.
*   **Professor's Script:**
    "To manage RAM efficiently, V8 divides its heap into distinct generations based on the 'generational hypothesis'—the fact that most objects die young. Newly created objects are placed in the Young Generation, which is small and fast. If an object survives several garbage collection passes, it is promoted to the Old Generation, which holds long-lived state data."

### Slide 14: Minor GC (Scavenger): The Dual-Space Copying Algorithm
*   **Visual Cue:** Horizontal process flow with golden chevron arrows linking From-Space -> Live Identification -> To-Space Copy.
*   **Slide Text:**
    *   **1. From-Space Allocation**
    *   **2. Live Object Scanning**
    *   **3. To-Space Copy & Swap**
    *   Active objects allocated inside the initial From-Space heap.
    *   Scanning pointers to identify which objects are still reachable.
    *   Copying live objects to To-Space, purging dead ones, and swapping roles.
*   **Professor's Script:**
    "The Scavenger algorithm handles Minor GC. It splits the Young Generation heap into two equal semi-spaces: From-Space and To-Space. Active allocations occur in From-Space. When cleanup is triggered, the engine scans for live objects, copies them in a contiguous block to To-Space, instantly purges the remaining dead objects in From-Space, and then swaps the names of the spaces. This is incredibly fast and prevents memory fragmentation."

### Slide 15: Major GC: Mark-Sweep-Compact Pipeline
*   **Visual Cue:** Horizontal process flow linking Mark -> Sweep -> Compact.
*   **Slide Text:**
    *   **1. The Marking Phase**
    *   **2. The Sweeping Phase**
    *   **3. The Compacting Phase**
    *   Traversing the object graph to mark all reachable memory nodes.
    *   Reclaiming unreferenced memory slots and returning them to the OS.
    *   Shifting live objects to contiguous memory to eliminate fragmentation.
*   **Professor's Script:**
    "When the Old Generation fills up, V8 triggers Major GC using the Mark-Sweep-Compact pipeline. First, it traverses the entire object tree starting from the roots to mark all active, reachable objects. Second, in the sweep phase, it identifies all unmarked slots and returns that memory to the operating system. Finally, it compacts the surviving objects into a single contiguous block to prevent fragmentation."

### Slide 18: Spectre & Meltdown: Shattering Sandbox Walls
*   **Visual Cue:** Vertical list explaining how CPU side-channel attacks allowed unauthorized cross-origin reading.
*   **Slide Text:**
    *   **Hardware Vulnerabilities**: CPU speculative execution bugs bypassed software sandboxes.
    *   **Speculative Side-Channel**: Timing attacks allowed reading cached values in CPU registers.
    *   **Cross-Tab Leakage**: Malicious Javascript in one tab could read memory from adjacent tabs.
    *   **Software Failure**: Traditional sandboxing was powerless against hardware-level read flaws.
*   **Professor's Script:**
    "In 2018, the security paradigm was shattered by Spectre and Meltdown. These hardware-level CPU vulnerabilities bypassed software sandbox walls. Because CPUs speculatively execute instructions to increase speed, they leave timing artifacts in the hardware cache. Malicious Javascript running in one tab could exploit these timing differences to read secrets—like active session cookies—from an adjacent tab sharing the same memory process."

### Slide 19: Site Isolation: The Process-per-Site Defense
*   **Visual Cue:** Vertical list panel detailing process-level origin separation as the ultimate Spectre shield.
*   **Slide Text:**
    *   **Process-Level Boundaries**: Isolating different domains into completely separate OS processes.
    *   **The Origin Barrier**: `google.com` and `attacker.com` never share a memory address space.
    *   **OS-Level Protection**: Leverages the host operating system's virtual memory map as a shield.
    *   **Mitigating Spectre**: Restricting memory reads to a single, isolated execution space.
*   **Professor's Script:**
    "Google's response to Spectre was Site Isolation. Software sandboxes were no longer enough; Chrome had to leverage the operating system's hardware-level virtual memory mapping. Under Site Isolation, Chrome uses a process-per-site architecture. A web page from `oikos.edu` and a page from `attacker.com` are forced to run in entirely separate operating system processes, ensuring they never share CPU memory space."

### Slide 20: The Strategic Trade-Off: Process Overhead vs. Security
*   **Visual Cue:** Vertical panel highlighting the 10% RAM penalty of process-per-site architecture.
*   **Slide Text:**
    *   **System Fragmentation**: Spawning multiple helper processes multiplies shared library overhead.
    *   **The RAM Penalty**: Site Isolation incurs a baseline 10% memory overhead on typical hosts.
    *   **The Strategic Dilemma**: Sacrificing local machine performance to guarantee data security.
    *   **Architectural Rule**: Security is never free; it is paid for in hardware resource allocation.
*   **Professor's Script:**

Spawning separate OS processes for every single frame and origin prevents memory leaks, but it fragments system resources. Because each process must load its own copies of V8, Blink, and shared libraries, Site Isolation incurs a baseline 10% RAM overhead. In IT strategy, we must consciously balance performance tradeoffs against security guarantees."

Under V3, the extension simply declares a JSON list of block rules, and Chrome executes them natively."
